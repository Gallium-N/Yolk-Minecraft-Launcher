# P0.2 返工：版本点击的加载与超时语义

> 一个小 commit：`fix(ui): loader probe timeout ladder and loader-list cache`

## 问题

P0.2 的实现里，8 秒 watchdog 是**硬超时**，而实测 `maven.fabricmc.net` 的 metadata 要 **12.5s**、
`meta.fabricmc.net` 要 **25.8s**。结果是：正常网络下用户点版本 → 必然 8 秒后看到错误条。
功能在真实环境里等于不可用，只在 QA 把超时调大时才"成功"。

根因有两层，都要修：

1. **8s 太短**：把"慢"当成"失败"。慢应该被提示，不该被判定为错误
2. **loader 列表没有缓存**：`MetaRepository.loadFabricLoaderVersions` 每次都联网（`MetaRepository.kt:122`），
   而 manifest 和 fabric profile 都有 TTL 缓存，就它没有

## 改法

### 1. 超时阶梯（替换单一 8s）

| 时刻 | 界面 |
|---|---|
| 0s | 骨架 3 行（现状，保留） |
| 3s | 骨架 + `正在连接 fabric maven…` |
| 10s | 骨架 + `网络较慢，仍在尝试` + 「取消」 |
| 30s | 错误条 + 「重试」「返回列表」（这才是硬上限） |

- 错误文案来自真实原因（`连接超时` / `HTTP 404` / `没有可用构建`），不要写"加载失败"
- 「取消」和「返回列表」都必须真能中断 UI 等待（generation 令牌已有，继续用）
- 30s 到点时若请求还没回来，直接放弃并**取消底层 job**

### 2. loader 列表缓存（真正解决首次慢之后的所有慢）

- `MetaRepository.loadFabricLoaderVersions(mc)` 改成：**先读缓存**（`data/meta/fabric/<mc>-loaders.json`，
  TTL 24h），缓存新鲜就直接返回，不联网
- 缓存过期 → **先返回过期缓存**（界面立即可用），同时在后台刷新；刷新失败只记日志，不打扰用户
- 缓存不存在 → 走网络，成功后落盘
- 缓存命中时日志写 `loaders cache hit <mc>`，便于验收

这样：第一次慢（12.5s，用户看到 3s/10s 的提示，能等），第二次**瞬间**，断网也能用。

## 验收（缺一不算过）

1. `build`/`test` 绿；一个 commit；新增 ≥3 单测（缓存新鲜直接返回不联网、过期先返回再刷新、
   刷新失败不影响返回）
2. **不借助任何 QA 属性**，真实网络点一个版本：
   - 贴出时间线：点击 → 3s 提示 → 10s 提示 → 列表出现（或 30s 错误）
   - 断言**没有在 8s 处出现错误条**
3. **缓存生效**：第二次点同一个版本 → 列表 ≤300ms 出现（贴计时日志）
4. **离线可用**：缓存就绪后把源指向不可达 → 再点同一版本 → 仍然出列表（来自缓存），
   界面无错误；点另一个未缓存的版本 → 30s 内出可读错误
5. 截图：3s 态、10s 态、成功列表、30s 错误态
6. 窗口级截图 + PID 断言
